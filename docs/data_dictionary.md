## 1. Overview & Architectural Conventions

This data dictionary formally specifies the relational data model for the ExamOps platform. Every entity, attribute, data type, nullability constraint, validation check, foreign key reference, deletion rule, and lifecycle semantic is defined below.

### Standard Identifier Conventions

| Entity | Public Identifier Pattern | Example |
|---|---|---|
| Student | `STU-<06d>` | `STU-000001` |
| Course | `CRS-<06d>` | `CRS-000001` |
| Enrollment | `ENR-<06d>` | `ENR-000001` |
| Exam | `EXAM-<YYYY>-<06d>` | `EXAM-2026-000001` |
| ExamRequirement | `REQ-<06d>` | `REQ-000001` |
| Room | `ROOM-<06d>` | `ROOM-000001` |
| RoomCapacity | `CAP-<06d>` | `CAP-000001` |
| Invigilator | `INV-<06d>` | `INV-000001` |
| Availability | `AVL-<06d>` | `AVL-000001` |
| Accommodation | `ACO-<06d>` | `ACO-000001` |
| ScheduleAssignment | `ASN-<exam-code>-<room-code>` | `ASN-EXAM-2026-000001-ROOM-000001` |
| SchedulingRun | `RUN-<YYYYMMDD>-<04d>` | `RUN-20261022-0001` |

### Primary Key & Historical Run Preservation Strategy
- All tables employ an internal surrogate primary key `id` of type `UUID` (generated by PostgreSQL `gen_random_uuid()`).
- All natural business identifiers (`student_code`, `room_code`, etc.) have explicit `UNIQUE NOT NULL` constraints.
- In `schedule_assignments`, `id` is a UUID PK, while `assignment_code` follows `ASN-<exam-code>-<room-code>`. The compound unique constraint `UNIQUE (scheduling_run_id, assignment_code)` allows historical runs to maintain stable assignment naming without collision.
- In `assignment_students`, the unique foreign key `run_exam_student_id UUID NOT NULL UNIQUE REFERENCES run_exam_students(id)` guarantees that an eligible student-exam pair is seated in **at most one room** across any split rooms of that examination.
- **Historical Immutability & Restrictive Deletions:** All child relationships on `scheduling_runs`, `schedule_assignments`, and master records use `ON DELETE RESTRICT`. Historical data is never cascaded away. Lifecycle transitions (`CANCELLED`, `SUPERSEDED`, `RESOLVED`) preserve records and append events to `schedule_events` and `audit_logs`.

## 8. Indexing Strategy & Performance Considerations

1. **Foreign Key Indexes:** Every foreign key column has an explicit B-tree index to eliminate sequential scans during relational joins.
2. **Conflict Overlap Indexing:** `schedule_assignments (scheduling_run_id, start_time, end_time)` accelerates temporal overlap interval queries.
3. **Capacity Date-Range Queries:** `room_capacities (room_id, effective_start, effective_end)` accelerates point-in-time capacity lookups.
4. **Active State Filtering:** Partial index on `accommodations (student_id) WHERE is_active = TRUE` ensures rapid lookups during snapshot construction.
5. **Partial Unique Publication Index:** `scheduling_runs (academic_period_id) WHERE (status = 'PUBLISHED')` physically enforces at most one active published schedule per academic period.
6. **Audit Chronology:** `audit_logs (created_at DESC)` and `schedule_events (created_at DESC)` ensure rapid page rendering for administrators.
